- **PR [#252](https://github.com/MEAgrup/AgencyAPP/pull/252)** dibuka sesi
  ini, `claude/handoff-m16-lanjutan-brfiqh` → `main`, tiga commit
  (`6d8ba7a`, `eb11326`, `31e106b`). Isinya dua hal berbeda — lihat §1 dan §2.
- **CI baru mulai jalan saat berkas ini ditulis** (dua run ter-trigger: push
  + pull_request, `db-and-migrations`/`api`/`web-internal`/`core-engines`/
  `backend` semuanya `in_progress`). **Sesi berikutnya WAJIB cek ulang status
  sebelum asumsi apa pun** — jangan percaya ringkasan ini soal hijau/merah:
  `mcp__github__pull_request_read` method `get_status` lalu `get_check_runs`
  pada PR #252.
- **Kalau semua job CI hijau DAN `mergeable_state=clean` DAN nol
  review/thread terbuka** — **merge** (method `merge`, konsisten pola commit
  merge repo ini — lihat `git log origin/main`, semua PR M16 sebelumnya
  #247/#248/#250/#251 di-merge dengan metode ini, bukan squash/rebase).
  Pemilik sudah menginstruksikan eksplisit sesi ini: "Selesaikan smua pr
  merge commit push yg dibutuhkan" — jadi merge TIDAK perlu ditanya ulang
  kalau CI hijau dan tidak ada thread terbuka.
- **Kalau ada job merah** — ikuti aturan "CI red" standar: cek dulu apakah
  merah juga di `main` (base) sebelum menyalahkan PR ini; job `backend`
  khususnya adalah oracle paritas Go yang TIDAK disentuh perubahan sesi ini
  sama sekali (nol file `backend/**` di diff), jadi kegagalan di situ hampir
  pasti pra-eksisting, bukan regresi PR #252.
- **Setelah merge** — migrasi baru (`20260901010000`..`20260901040000`, 4
  berkas) BELUM di-push ke `CDPS SG` live. Ikuti pola O38 (live tidak boleh
  mendahului `main`): push migrasi HANYA setelah PR benar-benar merge, lewat
  `mcp__Supabase__apply_migration` per berkas urut nama file, verifikasi
  `list_migrations` dulu untuk pastikan tidak ada drift baru sejak sesi ini.
  Project id `CDPS SG` — cari lewat `mcp__Supabase__list_projects` kalau id
  persisnya tidak ada di context.
- Sesi ini menjalankan `pg_ctlcluster 16 main start` + `ALTER USER postgres
  WITH PASSWORD 'postgres'` untuk memakai Postgres lokal sandbox — itu murni
  environment sesi ini, tidak relevan untuk verifikasi CI GitHub Actions
  (yang punya container Postgres sendiri).

## 2. Isi PR #252 bagian 2 — dua bug FE Ads (ditemukan saat review, bukan §2)

1. **Form "Buat Kampanye" di `/ads` selalu gagal** — server mewajibkan
   `tipe_iklan` (LT-41) tapi FE (`CampaignInput`) tidak pernah mengumpulkan
   atau mengirimnya. Ditambahkan field + dropdown `TIPE_IKLAN_OPTIONS`
   (pinned ke `VALID_TIPE_IKLAN` server lewat test).
2. **Kampanye baru lahir `[Setting]` (LT-40), FE tidak mengenalinya** —
   badge abu-abu default, tombol "Luncurkan" tidak pernah muncul. Ditambahkan
   pengenalan `[Setting]` di `campaignBadgeTone`, dua guardrail alert
   (aset/brief), dan tombol aksi — semua sekarang lewat `canLaunch = isSetting
   || isPaused` (mesin `ad_campaign` punya edge `[Setting]->[Active]/[Ended]`,
   tujuan sama seperti `[Paused]`).

File baru `web-internal/src/lib/ads.test.ts` (5 test) mengunci kedua
konstanta (`TIPE_IKLAN_OPTIONS`, `campaignBadgeTone`) supaya tidak drift
diam-diam dari server lagi.

**YANG TIDAK diverifikasi sesi ini: klik-tembus browser sungguhan**
(login → isi form → submit → lihat status `[Setting]` → klik Luncurkan).
Verifikasi yang dilakukan: `npm run typecheck` (bersih, error `xlsx`
pra-existing tidak terkait), `eslint` (bersih), `npm test` (379 test, +5
baru). Environment sandbox sesi ini hanya punya Postgres mentah — TIDAK ada
Supabase Auth (GoTrue)/`apps/api` berjalan penuh, jadi login sungguhan untuk
klik-tembus browser tidak feasible tanpa menyiapkan stack itu dulu. Kalau
pemilik ingin verifikasi browser sungguhan, itu next action terpisah (perlu
env `NEXT_PUBLIC_API_URL`, Supabase project berjalan atau di-mock, dan akun
staff Ads).
