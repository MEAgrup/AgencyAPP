| 2026-09-01 | **🟢 `web-client-portal` moved under `app.meagency.co.id/klien/*` — Next.js "multi zones", one shared domain, two still-separate apps/deploys/auth-realms.** Owner wanted the Client Portal on the same domain as `web-internal` (`app.meagency.co.id`), like the internal + vendor surfaces already are — but vendor and employee are actually the SAME Next.js project already (`web-internal/src/app/vendor/*`, LT-61), so the real ask reduced to: put the genuinely separate app (`web-client-portal`) under the same domain too, path is fine to differ (`/klien/login` etc., owner's own example). Raised first, before building anything, that a literal identical HOSTNAME would collide on the session cookie (`cdps_access_token`, `Path=/`, no `Domain=` scoping, shared by ALL realms) — an AM with an internal session open who also logs into the Portal in the same browser would silently kill one session or the other. Owner accepted that trade-off is real and asked to proceed anyway with the path-based approach, which still needed the collision fixed (below). **What's built**: (1) `web-client-portal/next.config.ts` gained `basePath: '/klien'` — every route/asset/`next/link` navigation in that app now resolves under `/klien` automatically; 3 plain `<a href>` tags (login/lupa-password/reset-password pages) were switched to `next/link` since a raw anchor does NOT get basePath-prefixed. (2) `web-internal/next.config.ts` gained a matching rewrite (`/klien/:path*` → the deployed `web-client-portal` URL, `CLIENT_PORTAL_URL` env override) — the exact same proxy technique this repo already uses for the `apps/api` backend rewrite, just fronting a second Next.js app; verified in the built `routes-manifest.json` (both apps build clean, full test suites green: `web-client-portal` 10/10, `web-internal` 390/390). Zero DNS/domain work needed — `app.meagency.co.id` already belongs to `web-internal`'s Vercel project, this is purely an in-app rewrite. (3) **Session cookie split** (the collision fix): `apps/api/src/lib/auth.ts` gained `CLIENT_PORTAL_SESSION_COOKIE` (`cdps_client_access_token`), `clientContactTokenFromRequest`/`requireClientContactActor` (read ONLY that cookie — deliberately a separate function rather than a fallback inside the general `tokenFromRequest`, because a fallback means whichever cookie is checked first always wins when both are present, silently resolving the wrong realm for whichever route loses the race), and parameterized `sessionCookie`/`clearedSessionCookie` to accept a cookie name. `POST /auth/login` picks the cookie name from the resolved actor; `GET /client-portal/me` (hit on every Portal page load) now uses `requireClientContactActor` exclusively so it can never be shadowed by a coexisting internal session; `POST /auth/logout` takes an explicit `{realm: 'client-portal'}` hint from the caller (default unchanged — every existing caller sends no body) rather than guessing from ambient cookie state, so logging out of ONE app never ends the other's session; `web-client-portal`'s own logout call was updated to send that hint. **One accepted, documented limitation**: `POST /auth/change-password` is the one handler BOTH realms call through the same code path — it tries the general cookie first, falling back to the client one only if absent, so in the narrow dual-session case (both cookies present) it always resolves the employee/vendor actor. Changing password from the Portal UI in that exact state fails with a confusing-but-safe `OldPasswordError` (no data crosses realms) rather than a wrong-account write — accepted rather than engineered around, since this route is only hit when actively changing a password, not on every page load like `/client-portal/me`. Full suite green post-change: `apps/api` 390/390 (+10 new cookie/actor tests), `tsc --noEmit` + `eslint --max-warnings 0` clean on `apps/api`/`web-client-portal`; `web-client-portal`/`web-internal` builds both confirmed the new config took effect (`required-server-files.json` basePath, `routes-manifest.json` rewrite entry). **Styling**: no work needed — `web-client-portal`'s CSS was already built to match `web-internal`'s token-for-token (pre-existing, `globals.css`'s own header comment says so). **Not done**: actually pushing/merging this branch, and the eventual Supabase Auth "redirect URL" setting for self-service email reset (still blocked on the pre-existing SMTP prerequisite) should target `https://app.meagency.co.id/klien/reset-password` once that infra exists. | Owner explicitly weighed the cookie-collision trade-off (raised via chat, not silently absorbed) and chose to proceed once a fix existed — the fix itself (separate cookie name + explicit per-route accessor, rather than an ambiguous fallback) was a technical necessity to deliver what was asked safely, not a product trade-off requiring a further ask. | Pemilik (explicit path-based-domain request, `app.meagency.co.id/klien/login` as the worked example) + Claude Code |
