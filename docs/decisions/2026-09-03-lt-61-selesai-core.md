| 2026-09-03 | **🟢 LT-61 SELESAI (core) — Live Stream vendor self-login: CDPS's first non-HRIS auth realm, built and tested.** Owner answered the 4 remaining `O63` mechanics via a second `AskUserQuestion` round: vendor gets BOTH `createSession` (sets its own schedule — "vendor pihak yang membuat jadwal, AM yang memberikan info jadwal ke klien") AND `confirmByVendor` AND `logResults` (not just results); `vendor_id` auto-copied from the client's Aktif Strategi `live` pillar; session TTL same as an employee's ("tetap login sepanjang hari"); provisioning by manual insert, no admin UI. **Design actually used, simpler than the original draft spec's "brand-new VendorActor type":** a vendor Actor reuses `permission.Actor` as-is — `employeeId = vendorId = vendors.id` (e.g. "VND-202608-0001", non-empty/legible/HRIS-disjoint by prefix, satisfies `sm_transition`/`audit_log.actor_employee_id` with **zero schema change to `audit_log`**), `role = makeRole({})` (all empty/false). Every other gate in the codebase keys off `role.*`, so a vendor Actor is a silent no-op everywhere except the explicit `vendorId` checks added to `packages/domain/src/livestream.ts` — no new actor type, no parallel routes; `apps/api/src/lib/auth.ts requireActor` tries the employee claim mapping first, falls back to `permission.actorFromVendorClaims`. **Write scope, pinned by construction:** `canVendorWriteSession` gates `createSession`/`confirmByVendor`/`logResults` (additive to the existing owning-AM/Director gate, never replacing it); `edge()` (the shared transition driver) requires an explicit per-call `allowVendor: true` opt-in that `reconcile`/`flagDiscrepancy` never pass — so no future edit to the gate predicate can accidentally let a vendor reconcile its own numbers, which is the entire point of that step. **Data model:** `live_stream_sessions.vendor_id` (nullable, stamped once at creation via `resolveLiveVendorId`, never updated — same immutability pattern as `data_confidence_tier`); a client is assumed to have AT MOST ONE live-stream vendor at a time (picks the most-recently-touched `live` pillar row when several exist) — documented limitation, not solved. **Auth realm:** new `vendor_accounts` table (Supabase Auth `auth_user_id` → `vendors.id`, "internal murni" RLS lock-down — same class as `employee_credentials`/`role_mappings`) + a second branch in `custom_access_token_hook` (employee branch untouched, same body/order, tried first) injecting ONLY `vendor_id` + `jwt_vendor_id()` RLS helper + `live_stream_sessions_select` amended for the vendor's own rows (read-side defense in depth; writes still go through `db()` service-role + the TS gate, O37 unchanged). Full spec: `docs/prd/CDPS_Module10_Addendum_LT61_Vendor_Portal_Spec.md`. | Reusing `permission.Actor` (rather than a parallel `VendorActor` type, as the pre-implementation draft assumed) cuts the entire diff to additive changes in one file (`livestream.ts`) plus the auth/wire boundary — every existing gate, the audit pipeline, `sm_transition`, and the wire mapper needed ZERO structural change, only a new field each carries through. The alternative (a separate actor type) would have forced either duplicating every call site that takes an `Actor` or a union type threaded through the whole domain/API layer for a population that, by design, is a no-op almost everywhere — cost with no corresponding safety benefit, since `role = makeRole({})` already achieves the same "can't accidentally gain employee permissions" guarantee structurally. Pinning `allowVendor` per `edge()` call site (rather than a blanket "vendor can write if vendor_id matches" inside `canManageSession` itself) trades a few extra characters at each of the 2 call sites for a durable guarantee that reconcile/flagDiscrepancy can never regress into vendor-writable by a future refactor of the shared predicate. | Pemilik (cakupan, 2 putaran) + Claude Code (desain + implementasi) |
