| 2026-08-31 | **🟢 M15-C2 Client Portal — 4-hour idle session TTL (spec §3.5, OQ-3) built; login rate limiting (§5.2, OQ-5) deliberately left open, with the reason logged.** Continuing the handoff's recommended next steps after the Supabase push (above) — both were flagged as small, app-level, unblocked follow-ups. **Idle TTL**: `web-client-portal/src/lib/idle-timeout.ts` (pure `isIdleExpired(lastActivity, now)`, unit-tested, plus `localStorage`-backed `touchActivity`/`clearActivity`/`checkIdleExpired` wrappers) — `api.ts`'s shared `request()` calls `touchActivity()` on every API call so no call site can forget it; `(portal)/layout.tsx` checks on mount and every 60s after, and past 4 idle hours calls a REAL logout (`POST /auth/logout`, which revokes the GoTrue session server-side — not merely a client redirect) then routes to `/login?reason=idle`, which the login page now renders as a BI notice. Zero DB migration, zero `apps/api` change — purely `web-client-portal`'s own layer, exactly as spec §3.5 prescribes (never a change to the shared Supabase project GoTrue TTL, which would also shorten employee/vendor sessions). **Rate limiting NOT implemented this entry** — found a real architectural snag while starting it, not a trivial follow-up as the previous handoff assumed: `POST /auth/login` (`apps/api/src/app/api/v1/auth/login/route.ts`) is ONE shared endpoint serving all three realms (employee/vendor/client-contact), branching by resolved Actor only AFTER GoTrue authenticates — by the time the code knows "this login is a client-contact", `passwordGrant` has already run, so branching post-hoc cannot throttle repeated bad-password attempts (the actual brute-force threat). Scoping a Portal-ONLY 10/IP/15min limit on a shared endpoint needs either (a) a spoofable header/origin check (weak — an attacker hitting the endpoint directly controls that header anyway), or (b) applying the limit to ALL THREE realms uniformly (simplest, robust, but exceeds the OQ-5 decision's literal scope — employee/vendor were explicitly said to keep relying on GoTrue's own protection only, §3.4). Either path is a real design call, not a one-line fix, and given the endpoint is genuinely shared, the persistent DB-backed counter the spec's own "app/DB layer" phrasing implies (in-memory won't survive Vercel's per-invocation serverless model) means a NEW migration to a production database mid-session — a second production-DB change beyond the one the owner explicitly authorized this session (the four pending migrations, entry above). Not done without asking first. **Recommendation for next session**: confirm with the owner whether the uniform-limit (b) simplification is acceptable before writing it. | Idle TTL had a clean, fully-contained, zero-infra-risk implementation path, so built it. Rate limiting's implementation surprised the previous handoff's "small, app-level" framing with a real shared-endpoint design question plus an implied second production migration — stopped and logged rather than picking silently, per CLAUDE.md's instruction to flag genuine ambiguity instead of guessing, and per the system-level norm of not taking a second unscoped production-database action without asking. | Claude Code |
