Mitigasi; akar pasti hang BELUM terbukti.** Gejala: Laporan PDT klien `CLI-202608-0008` (medikam hijamah, TikTok Shop, `client_platform_id=10`) berhenti di "Memuat laporan..." (juga butir 4–5 tab "Laporan PDT" dokumen feedback Tim Account). Log Vercel `agency-app-api`: `GET /api/v1/account/pdt/laporan` **Task timed out after 300 seconds** (03:03–03:23, 03:50–03:55, 04:25, 06:24, 08:21 UTC), padahal toko+periode yang SAMA sukses 100–200 ms di sela-selanya dan datanya tidak berubah sejak batch #40 (16 Okt). **Bukan ulangan LAPORAN-504-NPLUS1** (#493). **Yang TERBUKTI:** (1) setiap timeout 300 detik hari itu berpasangan 1:1, di detik yang sama, dengan log Supavisor `Client socket closed while state was idle (proxy)` — API menunggu balasan, pooler menganggap klien tidak menjalankan apa pun; `pg_stat_activity` bersih; nol galat checkout/pool di log Supavisor. (2) Pada 03:50–03:55 satu instance membuat `/me`, `/notifications`, `/clients`, login ikut menggantung (gejala "CDPS keluar sendiri" butir 4). (3) Lewat `db()` langsung, perakit memakai **5 dari 5** koneksi pool per request (`Promise.all` ±15 query). (4) postgres.js 3.4.9 MEMANG bisa mem-pipeline query autocommit: query TANPA parameter tidak `describeFirst`, koneksinya tetap "busy", dan query berikutnya ditulis di belakangnya sebelum `ReadyForQuery 'I'` query pertama tiba — dibuktikan probe kawat (proxy pengurai protokol). Di pooler mode transaksi itu jendela backend dilepas di bawah query yang menumpang. **Yang TIDAK terbukti:** pipelining autocommit itu terjadi pada jalur laporan — uji lokal tanpa fix (pool dingin maupun hangat, RTT tiruan 3 ms, 3× tiap) mencatat NOL kejadian, karena hampir semua query perakit berparameter (`describeFirst` ⇒ tidak pernah ditumpangi). Mekanisme hang di produksi tetap hipotesis. **Perubahan:** `bacaLaporanPdt` membungkus perakitan dengan `withTransaction` (1 koneksi ter-reserve; pooler memegang backend sampai COMMIT, jadi query yang antre di sana aman dari pelepasan backend); 29 fungsi pembaca menerima `Queryable` (tipe saja). Tes `pdt.test.ts` "PDT-LAPORAN-HANG": proxy pengurai protokol — laporan TikTok/Shopee wajib 1 koneksi dan nol `ReadyForQuery 'I'` saat masih ada query terkirim; kontrol membuktikan detektornya menangkap pipelining autocommit. | **Kenapa tetap dikirim walau akar belum pasti:** rebutan pool turun 5 → 1 koneksi per laporan, snapshot konsisten, risiko nol (nol perubahan SQL/bentuk respons). **Kenapa bukan `max_pipeline: 0`** (dicoba, DIBATALKAN): postgres.js hanya me-*reserve* koneksi `sql.begin` bila `sent.length < max_pipeline` ⇒ setiap transaksi gagal `UNSAFE_TRANSACTION` (34 tes `@cdps/db` merah). **Temuan terkait yang PASTI (belum diperbaiki di sini):** Simpan Batch (`tulisFaktaModulTerparse`) menyisipkan fakta SATU BARIS per pernyataan di dalam satu transaksi panjang, dan dengan `prepare:false` tiap pernyataan berparameter = 2 round-trip (Describe lalu Execute) — puluhan ribu baris per batch TikTok ⇒ menit, memegang backend pooler + kunci `pdt_upload_batch` (log 03:40: `konfirmasi-identitas` statement timeout "while locking tuple ... pdt_upload_batch"). Itu butir 3 dokumen feedback dan kandidat kuat pemicu rebutan saat insiden 03:40–03:55. **Verifikasi pasca-deploy:** log Vercel/Supavisor — pasangan timeout-300s + "idle (proxy)" pada route laporan. | Yohan Agustian (2026-10-19: "Cek bagian pembuatan laporan pdt, untuk klien ini, karena hasil report selalu gagal dan tidak terload") |
