| 2026-08-30 | **🟢 LT-61 follow-up — admin UI for vendor account provisioning, reversing the "no admin UI, manual insert only" call from `CDPS_Module10_Addendum_LT61_Vendor_Portal_Spec.md` §7/§8.** Owner asked to build the screen now (vendor count grew past "tiny", the condition that call was conditioned on). Scope: a new `web-internal` page `admin/vendor-accounts` (nav entry "Akun Vendor", gated same as the vendor record itself — Account lead / Director write, plus OD read per Phase 0 §4) to (1) list every vendor with its login status, (2) provision a new account, (3) deactivate/reactivate one (never delete — history stays). **Zero new tables** (134/37/30/67 all unchanged) — three new SECURITY DEFINER SQL functions in `20260904010000_lt61_vendor_account_admin_ui.sql`: `provision_vendor_account` (mints `auth.users`+`auth.identities`, same INSERT shape as `import_employee_credentials` — `apps/api` has no service-role key, so this SQL path is the only way to create a GoTrue user, per `20260729104209_admin_set_password.sql`'s header), `set_vendor_account_status` (mirrors `set_employee_banned` exactly), `list_vendor_accounts` (privileged read, `vendor_accounts` joined to `auth.users.email`). A partial unique index (`uq_vendor_accounts_active_vendor ... WHERE status_aktif`) enforces one ACTIVE account per vendor at a time while letting a deactivated-then-reprovisioned history accumulate. Domain: `packages/domain/src/vendor.ts` gained `listVendorAccounts`/`provisionVendorAccount`/`setVendorAccountStatus`, reusing `canManageVendor` for writes and a new `canReadVendorAccounts` (adds OD) for reads — the same `canReadAdmin`/`canWriteAdmin` split `admin.ts` already uses for `role_mappings`. A duplicate login email (across employees or other vendors — GoTrue enforces one globally) surfaces as a translated Postgres unique-violation rather than a pre-check, because `auth.users` is never read directly from TS (house convention: every touch of `auth.*` goes through a SECURITY DEFINER function). On plain Postgres (CI/local, no `auth` schema) provisioning throws a clear error rather than silently no-op'ing like `linkAuthUsers` — this runs from one explicit admin click, not a batch job, so it must not report false success; every guard BEFORE that point (gate, validation, vendor-not-found, already-has-an-account) is still fully tested there. Full suite green: domain 37 new/updated vendor tests, api wire + shape-parity (`VendorAccountWire` registered), web-internal nav + build. | Reuses `canManageVendor`/vendor CRUD's existing authority rather than inventing a separate provisioning role — the people trusted to edit a vendor's master record are trusted to decide whether it can log in.
