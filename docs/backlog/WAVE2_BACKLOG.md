## Epic M6 — Account & Service (wave entry: client → dispatched Briefs)

AC: a released client is invisible to individual AMs until assigned; assignment/reassignment writes an audit row; an assigned AM sees only own clients (permission test).
- **W2-02 · Service execution-path state machine** (M6 §2, STATE_MACHINES §6): each Service inherits a read-only `Requires Strategy Plan` flag and an Execution Path — Plan-gated (`[Awaiting Onboarding]`→`[Strategy Drafting]`→`[Strategy Submitted for Approval]`→`[Strategy Approved]`→`[Briefed]`→`[In Execution]`) or Direct (`[Awaiting Onboarding]`→`[Direct Breakdown]`→`[Briefed]`→`[In Execution]`); status lives on the Service, never the Client. AC: every transition enforced via the S0-05 engine; illegal transitions blocked with the specified BI message; the Client has no single onboarding status (derived from its Services). **Depends on: STATE_MACHINES §6 expanded to the M6 §2 granular set — see OQ-3.**
- **W2-03 · Strategy & Plan (`STR-`)** (M6 §4): one `STR-` per plan-gated Service (1:1) with the §9.3 fields; `[Strategy Drafting]`→`[Strategy Submitted for Approval]`→`[Strategy Approved]` with SPV/Head Account approve-or-revise loop (revision notes mandatory); Brief creation blocked until `[Strategy Approved]`; M6-OA-5 light addendum for in-spirit scope additions (no full restart). AC: Brief creation denied while the parent Plan is not Approved; revision notes mandatory on send-back; version/loop history immutable.
- **W2-04 · Service → Brief (`BRF-`) breakdown + Void cascade** (M6 §5): `BRF-` fan-out — one Service → many Briefs across divisions, from the approved outline (plan-gated) or straight (direct); Service advances to `[Briefed]` on first Brief, `[In Execution]` once any Brief leaves `[To Do]`; **upgrades the W1-12 Brief stub to the real entity** and wires the Void Service cascade (non-`[Approved]` child Briefs → `[Cancelled — Service Voided]`, terminal, logged). AC: Brief creation gated on the parent's execution path; void cascade leaves `[Approved]` Briefs untouched and never deletes; W1-12's cascade regression test still passes against the real Brief.
- **W2-05 · Brief dispatch + division-Kanban handoff contract** (M6 §6): Brief Kanban `[To Do]`→`[In Progress]`→`[Submitted]`→`[In Review]`→`[Approved]`/`[Revision Requested]`/`[Blocked]`/`[Cancelled — Service Voided]`; AM is the review proxy (client does not approve individual Briefs); **a Live Stream Brief routes to the M10 vendor tracker, not this Kanban**; per-Brief revision counter (read-only). AC: a Live-Stream-division Brief never enters the internal Kanban; the revision counter increments on each `[Revision Requested]`; the §9.4 handoff fields are all present.
- **W2-06 · Revision routing + rollup** (M6 §7): a revision routes back to the same division/PIC (never reassigned), AM feedback mandatory; revision counts roll up Brief → Service → Client for Health input; a Brief crossing 3 revisions surfaces SPV visibility (non-blocking, M6-OA-3, consistent with M12 Rule 15). AC: a revision request without feedback is blocked; Service/Client rollup sums are correct and recomputable; the 3-revision flag surfaces without blocking work.
- **W2-07 · Complaint door (`CPL-`)** (M6 §8): AM manually logs a `CPL-` (optionally linked to a Service/Brief), `Source` ∈ {`WhatsApp (AM-logged)`, `Client Portal`, `Sales`}; state machine `[Open]`→`[In Progress]`→`[Resolved]`→`[Closed]` (Closed = client-confirmed, distinct from Resolved); Severity Low/Med/High with M6-OA-4 Health penalties (−5/−15/−30); emits `EvComplaintLogged`; open-count feeds Health. ## Epic M12 — Task Execution (built EARLY — anchors M7/M8/M9 Speed)
> M12 is built here, before the execution divisions, and its canonical machine is validated against the M6 Brief (and a stub Task) so M7/M8/M9 plug straight in. It adds computed fields onto AST/BKG/BRF-as-task rows — "Task" is a role, never its own entity (DATA_MODEL note).
- **W2-08 · Canonical Task machine config + `[Blocked]` permission + block-request queue** (M12 §2, §5.3a): declarative transition table `[To Do]`→`[In Progress]`→`[Submitted]`→`[In Review]`→`[Approved]`/`[Revision Requested]`/`[Blocked]` (`[Open]` is a synonym of `[To Do]`, not a separate state); **only SPV/Lead may set `[Blocked]`**; staff/AM submit a block request that sits as a pending flag (`EvBlockRequestSubmitted` → SPV/Lead; `EvBlockRequestDecided` → requester). AC: a staff/AM actor cannot self-set `[Blocked]` (permission test); a block request creates a pending flag + notification, not a status change; every transition is audited.
- **W2-09 · Derived timing fields, recompute-from-log** (M12 §4–7, §5.1–5.4): `turnaround_time` (sum of `[In Progress]` intervals from first entry to first `[Approved]`, **excluding** all `[Blocked]` intervals), `revision_turnaround` (latest `[Revision Requested]`→next `[Submitted]`), `speed_score` (`turnaround_time` ÷ per-Task SLA, expressed %, **uncapped**), `revision_count` — all derived from immutable transition history, never stored mutable. AC: recompute-from-log reproduces every field exactly; blocked intervals are excluded; revision rounds do **not** reset `turnaround_time`; every enter/exit `[Blocked]` pair is logged and summed.
- **W2-10 · Per-Task SLA + quality flag + KPI rollup feed** (M12 §5.3, §5.5, Rule 14–15): SLA Target set **individually per Task** at Brief-breakdown time (Team Leader/SPV), **`speed_score` = N/A when a Task has no own SLA** (never backfilled from the Brief); `revision_count ≥ 3` auto-flags a Quality-review list (`EvRevisionCountFlag`, separate from and in addition to M9's KOL cap); per-staff/period rollup emits **three separate series** (avg Speed Score, Revision Count distribution, Hours Logged total) to M14 — never blended; Hours Logged shown next to Speed Score for context only. AC: a Task without its own SLA reports N/A (not a silent default); the ≥3 flag list surfaces; the three KPI series are never folded into one composite; Hours Logged never enters the score. **Note: M12 §6 leaves SLA-vs-Brief-window validation and the exact revision threshold open — see OQ-1/OQ-2; ship the default (threshold 3, no window enforcement) and gate any change on those decisions.**
